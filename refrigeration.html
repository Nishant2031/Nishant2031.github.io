Refrigeration Thermal Lab

A vapor-compression refrigeration simulator that predicts where a real system will actually run, using only the size of its heat exchangers and the temperatures of the fluids around it. Built in Python with CoolProp and Streamlit, and checked against a manufacturer's compressor datasheet.

The problem

In a thermodynamics class, a refrigeration problem usually hands you the evaporating and condensing temperatures, and you work out the COP. A real machine doesn't work that way. Nobody sets those temperatures; the system settles wherever the evaporator, the condenser and the compressor all agree.

I wanted a tool that answers the question an engineer actually asks: with this evaporator, this condenser and these water temperatures, how much cooling do I get, and at what COP?

How it works

  • Cycle. The four state points (compressor in and out, condenser out, valve out) come from CoolProp, with the compressor set by an isentropic efficiency and the valve treated as isenthalpic.
  • Heat exchangers. Each exchanger is split into 80 segments along the refrigerant path, so it handles the superheated, two-phase and subcooled zones separately, with an LMTD in every segment. Adding the segments up gives the UA the exchanger needs for a given duty.
  • Coupled solver. The unknowns are the evaporating and condensing temperatures. The solver moves them until the UA each exchanger needs equals the UA it actually has. If the first attempt fails, a bracketed fallback search takes over, and impossible inputs get a clear explanation instead of a crash.

Checking it against real data

I tested the model against all 57 published points of a Copeland ZR34K3E-TFD scroll compressor running R407C. The datasheet lists refrigerant mass flow and isentropic efficiency at every point. Neither is an input to my model, so both are honest, independent tests.

The check is sharp enough to catch real mistakes: it is how I found that R407C, a blend with about 5 K of temperature glide, has to use the dew point the way datasheets do.

A design trade-off

The design sweep re-solves the whole coupled system while one parameter changes. Growing the evaporator from 300 to 3,000 W/K raises the COP from 3.74 to 5.89, but most of that gain comes early: by the top of the range, each extra W/K buys only about 4% of what it did at the start. Past a point, a bigger evaporator mostly adds cost.

Bugs I found and fixed

  • A compressor map had capacity in Btu/h labelled as watts, which implied a COP of 25 when the Carnot limit was 13.5. I added second-law checks that now reject data like that automatically.
  • The plate heat exchanger was using round-tube laminar values (Nu = 4.36, f = 64/Re). I corrected them to parallel plates (Nu = 7.54, f = 96/Re) and added Gnielinski for turbulent flow.
  • R407C condensing pressure came from the bubble point instead of the dew point. The datasheet check confirmed the fix, taking the error from 4.6% to 0.14%.
  • R290 (propane) crashed on the default inputs because the solver got stuck next to a pinch point. The bracketed fallback solver fixed it.

Limits

Steady state only, with no refrigerant-side pressure drop, boiling and condensing coefficients set by the user, and dry air only. The heat-exchanger and coupled predictions have not yet been compared with a measured system; that is the next step, and the app's Test Validation tab is built for it.
